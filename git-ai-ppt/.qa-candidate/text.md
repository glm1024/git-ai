# CLI 和插件的 FAQ
| 问题 | 判断口径 |
| --- | --- |
| VS Code / JetBrains 插件能识别所有 agent 吗？ | 不能。只对已适配链路有效，例如 Copilot、Junie、AI Tab、Cursor hook 等；未适配插件只改文件时不能稳定判成 AI。 |
| Codex 在 VS Code 中改代码怎么识别？ | 关键看是否触发本机 Codex hook。hook 记录工具、模型、会话和文件前后状态；若绕过 hook 直接落盘，只能进入保存边界或 unknown。 |
| Cursor 这类 IDE agent 保存文件会触发 known\_human 吗？ | 可能会。保存事件来自编辑器文档管线，不能证明是人手敲；AI 归因仍应优先看 Cursor / Codex hook。 |
| known\_human 是怎么来的？ | VS Code/Cursor 保存文档时，扩展收到 onDidSaveTextDocument 后打 known\_human checkpoint；Auto Save、Save All、格式化保存也可能触发。 |
| unknown 应该怎么解释？ | unknown 只是“没有来源证据”，可能是人写、脚本生成、历史代码或未接入 AI；审计口径不要直接并成人类。 |

Kilo v5 与 Git AI 共存：场景与支持边界
两套链路会独立观察 commit；代码统计是否偏差，取决于双方是否认领同一最终代码行。

三类提交场景
过渡期支持口径
① 仅 Kilo v5 写入｜完全支持
Kilo v5 形成候选与提交事实；Git AI 没有对应 AI 行。
结果：Token、接受和入库按 v5 链路统计。
② 仅 Git AI 系列 Agent 写入｜完全支持
Codex、Claude Code、Kilo v7 等由 Git AI 记录；v5 没有候选行。
结果：按 Git AI 链路统计，单链路口径准确。
③ Kilo v5 + Git AI 混合写入｜有限支持
不同最终行分别统计，结果正确。
同一最终行被双方认领时，入库行数可能重复。
① 主线选择
Git AI 作为后续主链路；Kilo v5 逐步退出。
② 去重范围
本期不建设跨来源逐行去重，接受低频混合场景的少量偏差。
③ 指标口径
Token、生成/接受按实际调用和编辑过程分别统计；仅最终入库行重叠存在偏差。
④ 生命周期底线
commit / amend 可保留两条来源明细，但一次业务状态变更只能生效一次。
⑤ 适用边界
用于趋势与运营观察；不用于要求唯一行精度的结算或强审计。

支持结论：单链路完全支持；混合提交有限支持。当前接受少量重叠偏差，优先保障 Git AI 主链路演进。

# Git 生命周期归因：原生支持与后台闭环
Git AI 本地支持 Git Notes 随历史改写迁移；我们补齐生命周期上报、候选替换与目标分支确认。
| Git 生命周期 | Git AI 本地如何支持 | 二开上报逻辑 |
| --- | --- | --- |
| commit | checkpoint 汇总为提交级 Notes，绑定最终 SHA。 | 本地落盘后异步上报提交事实；失败保留队列重试。 |
| amend | 生成新 SHA，迁移或重建 Notes；最终 Notes 包含追加编辑。 | 上报替换关系，旧候选标记为被替换，新提交成为候选。 |
| rebase / 交互式 squash | 按旧、新提交映射迁移 Notes；旧提交被重写后的提交替代。 | 上报替换关系，旧候选标记为被替换，新提交成为候选。 |
| cherry-pick / revert / squash merge | 产生新提交并独立生成归因；源提交仍然有效。 | 只作为新提交上报，不会错误废弃源提交。 |
| reset 后退 / 恢复 | 本地状态随分支指针变化保留或重建归因。 | 上报指针迁移：回退废弃旧侧未确认候选；前进可恢复此前因 reset 废弃的候选。路径级 reset 不触发。 |
